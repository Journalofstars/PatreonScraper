# 技术细节

README 里放不下的实现细节都在这里。所有结论都是对着 Patreon 线上接口实测出来的。

## API 端点

| 用途 | 请求 |
| --- | --- |
| 创作者信息 | `GET /api/campaigns/{campaign_id}?include=creator,rewards` |
| 作品列表 | `GET /api/posts?filter[campaign_id]=…&sort=-published_at&page[count]=…&page[cursor]=…` |
| 单篇作品 | `GET /api/posts/{post_id}?include=…&fields[post]=…` |
| 单个媒体 | `GET /api/media/{media_id}` |
| 当前用户 | `GET /api/current_user` |
| **创作者的合集列表** | `GET /api/collection?filter[campaign_id]=…` |
| **单个合集（含全部作品和媒体）** | `GET /api/collection/{id}?include=posts,posts.images,…` |

**合集接口的路径是单数 `collection`**，写成 `collections` 会 404。

分页游标在 `meta.pagination.cursors.next`，请求时用 `page[cursor]` 回传。
合集接口**不支持分页**——`page[count]` / `page[cursor]` 都会被忽略，
一次就把 `post_ids` 里的作品全部返回（对常规规模的合集正合适）。

**`fields[post]` 白名单里必须包含 `content_json_string`**，否则服务端不会返回新版正文，
正文里内嵌的媒体就完全看不到（见下文）。

创作者 ID 的解析：主页 HTML 里的 `/api/campaigns/(\d+)` 最稳；
`parse_reference_all()` 会给出多个候选（去掉 `/c/` `/cw/` `/user` 等前缀后的段、
以及原始路径段），逐个尝试，Patreon 换新前缀时不会立刻失效。

## 合集（Collections）

创作者可以把自己的作品整理成合集（界面上是 `patreon.com/cw/<名字>/collections`，
单个合集是 `patreon.com/collection/<id>`）。

```jsonc
// GET /api/collection/2084280
{
  "data": {
    "id": "2084280",
    "type": "collection",
    "attributes": {
      "title": "| Multiple Character Videos |",
      "num_posts": 12,
      "post_ids": [165658323, 164828421, ...],   // 创作者自定义的顺序
      "post_sort_type": "custom",
      "num_draft_posts": 0,
      "num_scheduled_posts": 0,
      "thumbnail": { "original": "…", "default": "…" }
    }
  }
}
```

三种用法：

| 目的 | 请求 | 说明 |
| --- | --- | --- |
| 列出创作者的全部合集 | `GET /api/collection?filter[campaign_id]=…` | JSON:API 列表，含 `num_posts`、`post_ids` |
| 只取合集元信息 | `GET /api/collection/{id}?include=campaign` | 用来从合集 ID 反查创作者 |
| 取合集全部作品（含媒体） | `GET /api/collection/{id}?include=posts,posts.images,…&fields[post]=…` | **一次请求**拿回全部作品 |

`include` 列表由 `POST_INCLUDE` 逐项加 `posts.` 前缀拼成（见 `COLLECTION_INCLUDE`），
所以作品带的媒体字段和主页列表完全一致，可以直接复用 `extract_posts()`。

作品在 `included` 里的顺序**不保证**等于 `post_ids` 的顺序，
`fetch_collection_posts()` 会按 `post_ids` 重排，保持创作者自定义的展示顺序。

**合集不是独立内容源**：实测某创作者 18 个合集、去重 133 篇作品，
100% 都在主页列表的 152 篇里。所以合集的价值是「按题材挑」，
而不是「主页列表漏了内容」。界面上因此做成**下拉筛选**（客户端过滤 `post_ids`），
并且只在「这个合集一篇都没加载过」时才去请求合集接口。

## 为什么会出现「名称相近的重复文件夹」

**症状**：同一个作品下出现两个并排的文件夹，名字只差最后几个字符：

```
…2025-11-19_Your Bratty Fox Girl … (Brat _ Blowj        ← 79 字符，里面是几百 MB 视频
…2025-11-19_Your Bratty Fox Girl … (Brat _ Blowj_       ← 80 字符，只有 post.json / post.txt
```

**成因**：目录名的截断方式变过（`util.sanitize_filename` 从"硬截断到 80 字符"
改成了"在 80 字符内尽量按词边界截断"）。于是：

1. 旧版本建了 `…Blowj_`，媒体都下在里面，状态库记的是这个路径；
2. 新版本按新规则算出 `…Blowj`；
3. 逐条检查媒体时，状态库通过记录找到 `…Blowj_` 里的老文件，判定「已下载」→ 跳过；
4. **但元数据仍然写进 `task.dest_dir`，也就是新算出来的 `…Blowj`**。

结果新目录里只剩 `post.json` / `post.txt`，旧目录里的媒体还在原地。

**程序侧修复**：`downloader.reuse_existing_directory()`

在 `build_tasks()` 里，除了「目录被别的作品占用」之外，还先问一句：
**这篇作品是不是已经下在别处了？**

```python
directory = post_directory(config, campaign, post)      # 按当前规则算
reused = reuse_existing_directory(config, campaign, post, state)
if reused:
    directory = reused                                  # 沿用旧目录
```

判定完全基于 `StateStore.resolved_dirs_for_post()` —— 把这篇作品的每条媒体记录
解析成真实路径，看它们实际落在哪个目录；再从这个目录**逐级向上**找带
`post.json` 且作品 ID 吻合的那一层（所以分段子目录、多层模板都认得出）。
路径必须仍在当前下载目录内，否则放弃。

**已经产生的残留**：用 `tools/clean_duplicate_folders.py` 收拾，默认只报告：

```bat
python tools\clean_duplicate_folders.py                 :: 预览
python tools\clean_duplicate_folders.py --apply         :: 真删
```

它以 `post.json` 里的作品 ID 分组（不是靠名字像不像），只删满足下面条件的：

* 同一作品 ID；
* **同一父目录**（真正的重复是并排兄弟；`split_sections` 的分段子目录在根目录之内，排除）；
* **名字互为前缀**（截断变化留下的签名，进一步排除 `13_…` / `10_…` 这种分段名）；
* 该目录为空壳，**或者**它里面每个媒体文件在保留目录里都有同名同大小的副本。

四条同时满足才删，宁可漏报不误删。

## 预告（video_preview）与完整版可能是**两个不同的 mux 资产**

这是最容易下错文件的一个坑。

`video_preview` 有两个时长字段：

```jsonc
"video_preview": {
  "duration": 46.997,              // 预告片自己的长度
  "full_content_duration": 1165.233, // 完整版的长度
  "url": "https://stream.mux.com/8XyV8FWxKqKTV2NsRdLnm5iFYKoAoNmhqCijkhBPP8Y.m3u8?token=…"
}
"post_file": {
  "duration": 1165.233,
  "full_content_duration": 1165.233,
  "url": "https://stream.mux.com/qL01G8vvNP9rbanBJsa6AD94FdFuPxEUWwPOAo8KLb9w.m3u8?token=…"
}
```

**两个 URL 里的播放 ID 不一样**，而且实测（读 m3u8 的 `#EXTINF` 求和）：

| 作品 | `video_preview` 的 ID | `post_file` 的 ID |
| --- | --- | --- |
| 163617400 | 16.70 秒（4 段） | **737.50 秒（148 段）** |
| 163711168 | 25.25 秒（6 段） | **965.87 秒（194 段）** |
| 164828421 | 47.00 秒（10 段） | **1165.27 秒（234 段）** |

预告那个 ID **只给短片**，和 `video_preview.duration` 完全吻合。

### 踩过的坑

有的作品里，relationship 中 `media` 对象的 `download_url` **恰恰指向预告那个 ID**：

```
media 705328695  mime=application/x-mpegURL
  download_url = https://stream.mux.com/8XyV8…/highest.mp4?token=…
                 ^^^^^^ 和 video_preview 同一个播放 ID = 46 秒预告
```

早期逻辑把"带 mux 地址的 media"一律当成完整版，于是：

1. 该 media 抢先把 `_has_mux_full` 置为 `True`；
2. 处理 `post_file` 时看到"已有完整版"就跳过；
3. **结果下到 46 秒的预告，还标成完整版。**

而且因为 HLS 视频没有 `size_bytes`，`verify_size` 无从校验，这个错误会**永久留在状态库里**（记录的文件存在就算已下载）。

### 现在的规则

1. `_preview_playback_id()` 先判定 `video_preview.url` 是不是**独立**预告资产：
   只有当 `duration < full_content_duration × 0.95` 时才算。万一两者相等
   （预告就是整片），就不当预告，避免把内容丢掉。
2. `collect_media_object()` 里凡是播放 ID 命中预告集合的：
   - 标记 `is_preview=True`；
   - 默认（`include_previews=False`）直接丢弃；
   - **绝不设置** `_has_mux_full`，把机会让给 `post_file`。
3. `derive_mux_video()` 也拒绝从预告的播放 ID 推导，防止兜底路径再次误判。

> 注意：**不能**因为"有 `video_preview` 就一定有完整版"。有的是只有预告的
> 免费试看贴，这时默认不产出任何视频才是对的。

## 媒体地址从哪来

**图片**：`media.image_urls` 里按画质取
`original` → `default_large` → `default` → `thumbnail` 逐级回退。

**视频**有三种情况：

1. `media.download_url`，`mimetype` 为 `application/x-mpegURL` 时通常是
   `https://stream.mux.com/<playbackId>/highest.mp4?token=…`，即**完整视频**；
2. `post.attributes.post_file.url` 里的 `.m3u8`（新版格式），带同一个播放 ID，
   可以换成 `highest.mp4`；
3. 其它 `video/mp4` 直链多半是 30 秒预览，由「视频预览片段」开关控制。

**mux 令牌必须验 `aud` 字段**：

| 令牌 | `aud` | 用途 |
| --- | --- | --- |
| 视频 | `v` | 可取 `highest.mp4` / `.m3u8` |
| 封面图 | `t` | `image.mux.com/.../thumbnail.jpg`，拿去请求视频会 **403** |
| 故事板 | `s` | `storyboard.vtt` |

程序解码 JWT 的 payload（只读，不验签名），只接受 `aud` 为 `v` 的令牌，
并跳过 `/text/`、`/storyboard`、`/thumbnail`、`.vtt`、`.json` 这类非视频地址。

## mux 受保护播放（无静态 MP4）

部分视频的令牌里带 `playback_restriction_id`：

```json
{"sub": "Ofqx…", "exp": 1791284400, "aud": "v",
 "playback_restriction_id": "Ir02FmqsqUnMIpEqH89MdlvWa15QwOo6dCnelCtSI9YI"}
```

此时 mux **不提供任何静态 MP4**，请求 `highest.mp4` 会得到
`404 {"error":{"messages":["MP4 does not exist"]}}`；但 `.m3u8` 是 200 可用的
（签名在 URL 里，不是内容加密）。

处理方式：

1. 识别到 `playback_restriction_id` 就跳过静态 MP4，直接用 HLS；
2. `.m3u8` 主播放列表 → 选最高码率 → 顺序下载分片拼接；
3. 这些分片是 **MPEG-TS**（没有 `EXT-X-MAP`），所以拼出来不是合法 MP4，
   再用 **ffmpeg `-c copy`** 无损封装成 MP4；
4. 没有 ffmpeg 时保留 `.ts`，扩展名按实际格式决定。

下载器还支持 `#EXT-X-BYTERANGE` 分片（按 `Range` 头请求）。

## 新版富文本正文（`content_json_string`）

Patreon 有两代编辑器：

- 旧版：正文在 `content` 字段（HTML）；
- 新版：正文在 `content_json_string`，是一个 ProseMirror 文档，
  **媒体以 `media_id` 内嵌在正文里**：

```json
{"type":"video","attrs":{"fallback_strategy":"fallback","media_id":"739888749"}}
```

这类媒体**完全不在** `relationships`（`media` / `images` / `attachments_media`）里，
所以只看关系字段的话，无论从主页列表还是从单篇作品都抓不到——
一篇「索引贴」里 21 个视频只会显示 1 张封面图。

处理方式：

1. `fields[post]` 里带上 `content_json_string`；
2. `parse_rich_content()` 遍历文档，收集所有内嵌 `media_id`；
3. 对每个 ID 调 `GET /api/media/{id}` 取回媒体对象（响应含 `download_url`，
   结构与关系字段里的一致）；
4. `media_resolver` 会先用页面响应里已有的媒体对象，没有再发请求——
   普通作品因此**零额外请求**。

因为要逐个请求，设置里给了开关「正文里内嵌的媒体」，默认开启。

### 按部分分组

正文里每个媒体前面的那段文字就是它的标题，但**不一定是 heading**，也可能是
`blockquote`：

```
[3]  blockquote 'Your Bratty Girlfriend Loves Bond*ge...'   ← 标题
[4]  video       739888749
[16] heading L2  'Bully Series Arcs'                        ← 分类
[19] heading L3  'Part 1 [Handj*b] :'                       ← 标题
[21] video       739906981
```

`parse_rich_content()` 因此按这个规则分组：

- 维护 **heading 层级栈**（遇到更深层 heading 时清掉更深的层）；
- 维护「最近一段非空文字」（heading / blockquote / paragraph 都算）；
- 每个媒体的小标题 = **heading 路径 + 最近的文字**，去掉重复项。

这样上例里两个同名的 "Part 1" 会分别得到
`Bully Series Arcs - Part 1 [Handj*b]` 和 `School Festival Arc - Part 1 [Handj*b]`。

「帖子内含多个部分时，每个部分单独建子目录」打开后，`build_tasks()` 按
`MediaItem.section` 分目录，每个目录内文件从 `01_` 重新编号；
**只有 2 个以上部分的帖子才拆分**，普通帖子不受影响。

## 增量判断：相对路径而非绝对路径

`data/state.json` 里每条记录同时存：

```jsonc
"171238686:m756567987": {
  "rel":  "NSFW VTuber Roleplay Videos\\2026-10-03_标题\\02_封面.png",  // 判断用这个
  "path": "G:/bb\\NSFW VTuber Roleplay Videos\\2026-10-03_标题\\02_封面.png",
  "size": 301618, "kind": "image"
}
```

`MediaItem.key` 是稳定标识（`{post_id}:m{media_id}`，没有 media_id 时用去掉签名
参数的 URL 指纹 `stable_url_key()`），所以多次抓取能对上同一条记录。

`StateStore._candidate_paths()` 只认**当前下载目录内**的位置，按可信度排序：

1. `<当前下载目录>/<rel>`；
2. 记录的绝对路径，**前提是它仍在当前下载目录内**；
3. 用绝对路径的尾部在当前下载目录里逐级找回（老记录 / 已换目录）。
   这属于猜测，**必须大小完全吻合**才认，避免同名文件误判。

命中后就地**自愈**：把 `path` / `rel` 更新成新位置，下次直接命中。
所以把整个下载目录从 `G:/bb` 搬到 `E:/bb` 再改设置，依然算已下载；
而不在当前下载目录里的文件一律不算——这就是「只考虑下载目录中的内容」。

## 几个不直观的坑

| 现象 | 原因 |
| --- | --- |
| 静态 MP4 全部 404 | 受保护播放不给静态 MP4，只能走 HLS（见上） |
| 视频 403 | 误用了封面图令牌（`aud: "t"`），或令牌过期 |
| 下载体积和接口报的 `size_bytes` 不一致 | 接口报的是源片大小，程序下的是 `highest` 清晰度并重新封装。所以这个数字**只用于界面显示**，不参与「已下载」校验，否则每次都会重下 |
| 字幕 / 故事板被当成视频 | 已按 `aud` 和路径特征排除 |
| 创作者页 `/cw/xxx` 解析失败 | 路径前缀表已覆盖 `c` / `cw` / `user` 等 30 多个，并会跟随跳转 |

## 限流与重试

`PatreonClient.request()` 统一处理：

- `429`：读 `Retry-After`，等待后重试（上限 120 秒）；
- `5xx` / 网络错误：指数退避重试，次数由设置里的「失败重试次数」决定；
- `401 / 403`：抛 `AuthError`，界面提示重新登录；
- `404`：抛 `NotFoundError`；
- 返回 HTML 而不是 JSON：提示登录失效或触发了人机验证。

请求间隔由设置里的「请求间隔」控制，默认 0.35 秒。
